# LoRA training-recipe forensic audit

**Scope and guardrails.** Read-only review of `train.py`, `checkpoint_adapter.py`, the frozen run configs/logs/checkpoint manifests, `DEGENERACY_AUDIT.md`, the archived fresh-60 aggregate comparison, and train/dev reference labels via aggregate counts only. No models were loaded; no inference or training was run; no test references or row-level test predictions were opened. No training source was changed. Per-class counts below are aggregates, not a rereview of individual labels.

## Bottom line

**No clear implementation defect explains the bad LoRA decisions.** The saved evidence supports that both query and candidates pass through the same differentiable backbone, the typed head scores each candidate separately, choice/Noul targets are aligned correctly, numeric score levels retain their configured ordering, and the adapter/checkpoint paths are validated. The runs are not “untrained”: each completed 1,380 optimizer updates; nonzero LoRA and head tensors, per-step LoRA gradients, and finite losses are recorded.

There are, however, concrete **recipe/evaluation weaknesses**: very low-capacity adaptation (rank 2 on q/v in only the final block), only 460 train questions over a highly heterogeneous grouped split, an underspecified 200-question dev split made from just two of nine components, mixed-task aggregate-loss checkpoint selection without per-type dev metrics, and an unseen-length shift in fresh-60. These are plausible explanations, not proof of a single cause. The archived outputs show the LoRA models are distinct and input-dependent, but Noul and score argmaxes collapse to one answer each.

## What the source does (and does not) show

- **Gradient path and candidate features:** `PreferenceModel` calls the differentiable decoder on the query plus all candidates, gathers each actual final-token hidden state, L2-normalizes it, then passes the query/candidate vectors to `TypedScorer` (`train.py:323–338`). The scorer broadcasts query and constructs candidate-specific `[q, c, q*c, abs(q-c)]` vectors before a shared `4096 -> 192` GELU projection and separate choice/Noul/score scalar heads (`:307–320`). So it is not a query-only score or accidental repeated candidate scalar. Per-step nonzero LoRA gradients and smoke loss decrease are in the saved records.
- **Adapter:** `checkpoint_adapter.py:52–97,141–166` strictly maps and loads the decoder; `:169–210` freezes base weights and inserts FP32 residual LoRA into selected attention projections. Trainer runtime guards verify frozen BF16 base, trainable FP32 LoRA, and that no other backbone parameters are unfrozen (`train.py:534–555`). Saved compiled-text parity is >0.9995 cosine for query and candidate. No loading/namespace bug is indicated.
- **Target/polarity:** choice labels are resolved against the ordered option keys; Noul explicitly maps false to `unsupported` index 0 and true to `supported` index 1 (`train.py:97–120`). This is consistent with the archived evaluator checks in `DEGENERACY_AUDIT.md`; false is not an inverted decode bug.
- **Score objective:** keys and their numeric `values` are built in the same `levels` order, with target index found by label (`:109–120`). The objective combines soft ordinal cross-entropy over numeric distance normalized by that question’s rubric span with Huber loss on span-normalized expected-value error (`:398–416`). This is coherent and candidate-dependent; no numeric index/value inversion or missing normalization is apparent. Its `0.75` weight on normalized Huber / `0.25` on ordinal CE is a design choice, not a demonstrated coding bug. It does mean aggregate dev loss mixes custom score loss with categorical CE, so aggregate loss is not a clean common-scale selector across types. Raw expected-value MAE across differently scaled rubrics is likewise hard to compare; prefer per-question span-normalized MAE and ordinal MAE.
- **Selection:** `eval_cases` returns only a single mean loss and pooled exact accuracy (`:459–472`). Checkpoints are selected by aggregate mean loss (`:741–745`); per-type dev accuracy, CE/calibration, and prediction/selection histograms were not saved. For Qwen, dev accuracy rises `38.5% -> 41.5% -> 44.5%` while loss worsens `0.959 -> 1.004 -> 1.013`; for Harrier it rises `39.5% -> 41.0% -> 41.5%` while loss worsens `0.948 -> 0.970 -> 0.972`. Thus best epoch 1 is correct under the *declared loss rule*, but that rule demonstrably does not select the highest-accuracy epoch. Do not call it a training-code bug; it is a material objective/selection mismatch.

## Aggregate train/dev priors and constant-position policies

The current configs use the same fixed grouped split for both model families: 460 train and 200 dev questions (300/120 case IDs split into 180/120 train/dev cases; only 11 train families vs 4 dev families, in nine connected components total). Per-type aggregated gold-position histograms and best fixed-position policy accuracy are:

| Split/type | n | Gold position counts | Best single position policy |
|---|---:|---|---:|
| train choice | 140 | 0:37, 1:47, 2:34, 3:13, 4:9 | 47/140 = 33.6% |
| dev choice | 100 | 0:26, 1:24, 2:21, 3:18, 4:5, 5:6 | 26/100 = 26.0% |
| train Noul | 160 | unsupported/false:90, supported/true:70 | 90/160 = 56.3% |
| dev Noul | 60 | unsupported/false:32, supported/true:28 | 32/60 = 53.3% |
| train score | 160 | 0:50, 1:35, 2:51, 3:18, 4:6 | 51/160 = 31.9% |
| dev score | 40 | 0:10, 1:9, 2:13, 3:6, 4:2 | 13/40 = 32.5% |

These are position-policy baselines, not label identities: choice labels are heterogeneous across rubrics, and score levels vary in number/order. A global “always workable” label is not a valid train/dev policy across those varied rubrics. The split also shifts cardinality: choice training has no 6-candidate examples, whereas 20/100 dev choice examples have six candidates (training max five). Only two grouped components are held out, so per-type dev estimates are especially noisy and may conflate family/domain and candidate-count shifts.

The archived same-split head-only baseline makes the practical gap concrete: Qwen is 48.0% question-weighted dev accuracy vs LoRA 38.5%; Harrier is 57.0% vs 39.5%. On Harrier dev, head-only is 38% choice / 83.3% Noul / 65% score, while the LoRA dev log has no saved per-type prediction results. Those head-only numbers are much higher than the constant-position policies above, especially for Noul/score, so those dev tasks are learnable by the frozen-embedding comparator; the aggregate LoRA dev metrics alone cannot locate its failure type.

## What the archived fresh-60 aggregate permits us to say

Per `DEGENERACY_AUDIT.md` and `eval/fresh60/comparison-core-six.md`, both LoRA runs predict false/unsupported for all 60 Noul items (30/60 correct, exactly chance on this archived set) and `workable` for all 60 score items (20/60 correct). Their choice picks vary, rather than always selecting the first candidate. Paired LoRA models have distinct raw logits and checkpoint hashes; do not infer shared weights or a broken loader from matching winners.

The exact same-460 Qwen head-only comparison scores 35.0% choice and 61.7% Noul vs Qwen LoRA 25.0% and 50.0%; however, score accuracy is 10.0% for that head-only model vs LoRA 33.3%, and LoRA has better archived score expected-value / ordinal MAE. Harrier same-460 head-only is 28.3% choice, 58.3% Noul, 33.3% score. Thus “head-only always won” is not supported; the Qwen head-only model is better on choice/Noul but worse on score. Do not use these heldout metrics for tuning.

This is evidence of a **real output-quality collapse**, not an implementation mismatch. It is also not well-calibrated useful discrimination: archived Noul probabilities cluster near 0.5; score logits separate candidates somewhat but retain one winner. The aggregate 30/60 for constant false implies a 50/50 label split on that archived Noul subset; this is only inference from the already-published aggregate, not a new test-label audit.

**Length confound:** training text lengths are p50 24, p90 167, p95 179, p99 257, max 266 tokens; trainer rejects above 288 and never truncates. The frozen fresh-60 report says 180 inputs exceeded the training max, up to 375 tokens, evaluated under a 512-token inference policy with no truncation. This is substantial extrapolation and can hurt either model, but cannot explain the same-split dev gap, and does not prove the Noul/score constants are caused by length. Fresh-60 accuracy must not be used to tune the next recipe.

## Prioritized next run (no test-guided tuning)

1. **First fix observability and selection, not model hyperparameters.** On the exact existing grouped split, save per-type dev accuracy, CE, normalized score MAE/ordinal MAE, gold/predicted position histograms, mean/max confidence, entropy, and reliability bins for every epoch and for the frozen-embedding comparator. Select with a predeclared per-type macro dev objective (e.g. equal-weight per-type dev CE, score CE plus normalized ordinal/expected-value metric stated in advance), and report accuracy independently. This will reveal whether the constants already occur on dev and avoid one task dominating a mixed loss. The tiny dev has only 2 held-out components; treat it as a diagnosis, not robust generalization evidence.
2. **Run a clean capacity control on the same data/split:** identical typed 192-wide MLP with backbone fully frozen (no LoRA) versus current LoRA+same head. This isolates LoRA value from the head/optimizer/objective. Keep question batch 1, no accumulation, existing 288 reject-not-truncate policy, and early stopping. If frozen typed MLP is also constant while the same-split cached linear head is strong, isolate head architecture/optimization/feature-distribution differences before expanding LoRA.
3. **Only if LoRA adds value in that control, test adaptation scope as one predeclared ablation:** current one final q/v block rank 2 versus two upper q/v blocks at rank 2 (or one rank-4 block, not both changes together). Current config `train.py:54–60` adapts just the final block, rank 2, alpha 4, LR 1e-4, three epochs; this is a conservative capacity ceiling, plausible under-adaptation rather than a broken graph. Compare on grouped dev diagnostics only; no sweep against test.
4. **Treat score and class calibration separately.** Keep current score loss for the first diagnostic control; if its per-type results warrant an objective experiment, compare the existing ordinal+Huber objective to ordinal-only, with the same normalized metrics and identical split. Avoid class reweighting or temperature fitting until per-type training/dev class and confidence diagnostics show a specific need. Training Noul is 56/44 and dev 53/47, so simple train prior imbalance cannot explain always-false outputs. For choices, account for differing candidate counts and the train/dev six-choice mismatch when interpreting dev.
5. **Length diagnosis:** report dev metrics stratified by train-supported token-length bins (aggregate only). Do not truncate or silently exclude long strings. To test extrapolation later, preregister a train/dev protocol that covers the intended length regime; preserve an untouched evaluation set.

**Resource contract:** the completed local-lowmem runs fit: the freeze manifest records ~5.01 GiB process peak for each, below the 6 GiB early-stop / 8 GiB hard limit, with system swap unchanged. Pilot artifacts are incomplete; do not mistake `pilot-qwen-lowmem-v2` (20 steps, no completed epoch) for the selected Qwen run. For the next run, retain frozen BF16 base, batch 1, no accumulation, upper-block checkpointing, 288 cap with rejection, OS physical-footprint sampling every optimizer step, hard stop at 6 GiB (prefer a lower preregistered stop if needed for margin), and abort immediately on any swap increase. Run one model/control at a time, not parallel. These are the proven saved low-memory run settings; do not raise either memory ceiling.
